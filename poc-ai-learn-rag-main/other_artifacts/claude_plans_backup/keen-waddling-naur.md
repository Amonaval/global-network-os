# Fix: XSS via Unsanitized csrftoken Cookie in web-engine-loader.js

## Context

A security scan (`X-RTC-ATTACKTYPE: XSS`) found that an attacker can inject arbitrary script into the served `index.html` by sending a request with a crafted `csrftoken` cookie value such as:

```
csrftoken=--></script><script>alert(4555149)</script>
```

The Node.js server reads this raw cookie value, substitutes it directly into the HTML template for the `<RDP_CT>` placeholder (which sits inside a `<script>` block), and writes that HTML to disk as the shared `index.html` served to all users. This is a **stored XSS** — every user that subsequently loads the app receives the injected script until the file is overwritten.

---

## Architecture Flow (how it works today)

```
Browser (GET /)
  → Cookie: csrftoken=<value>
      ↓
web-engine-loader.js : line 334
  const csrfToken = req.cookies['csrftoken']   ← raw, no validation
                    ? req.cookies['csrftoken']
                    : req.csrfToken();
      ↓
modifyIndex() : line 346
  result = data.replace(/<RDP_CT>/g, csrfToken) ← injected into <script> block
  fs.writeFile(index.html, result)              ← written to shared on-disk file
  res.sendFile(index.html)
      ↓
Browser receives index.html
  window.process.env.RDP_CT = "<csrfToken>"    ← now attacker-controlled
      ↓
DALConfig['rdpCt'] populated from window.process.env.RDP_CT
      ↓
DALCommonUtils.getCsrfToken()                  ← returns DALConfig['rdpCt']
      ↓
XHR header: x-rdp-ct: <csrfToken>
```

The injection point in `index-template.html` (line ~358):
```html
<script>
    window.process = {
        env: {
            NODE_ENV: 'production',
            CDN_URL: '<CDN_URL>',
            RDP_CT: '<RDP_CT>'       ← attacker payload lands here
        }
    };
</script>
```

A payload of `--></script><script>alert(1)</script>` closes the `<script>` block and injects new script.

---

## Fix

**File:** `web-engine-loader.js`  
**Line:** 334

### Root cause
The server trusts and reuses an existing `csrftoken` cookie value verbatim. Legitimate CSRF tokens (generated by `csurf`) contain only base64 characters (`[A-Za-z0-9+/=]`). An HTML-special character (`<`, `>`, `"`, `'`, `&`) can never appear in a valid token — their presence indicates a tampered or injected value.

### Change

Replace:
```js
const csrfToken = req.cookies['csrftoken'] ? req.cookies['csrftoken'] : req.csrfToken();
```

With:
```js
const VALID_CSRF_TOKEN = /^[A-Za-z0-9+/=_\-]{10,128}$/;
const rawCsrfCookie = req.cookies['csrftoken'];
const csrfToken = rawCsrfCookie && VALID_CSRF_TOKEN.test(rawCsrfCookie)
    ? rawCsrfCookie
    : req.csrfToken();
```

**Why this works:** Any cookie value containing `<`, `>`, or other HTML/script-breaking characters fails the allowlist test, so `req.csrfToken()` generates a fresh safe token instead. The regex matches exactly the character set that `csurf`'s random base64 output produces, so valid tokens pass through unchanged.

**No other files need changes.** `DALCommonUtils.js` and `index-template.html` are not the source of the vulnerability.

---

## Verification

1. Replay the attack request with `Cookie: csrftoken=--></script><script>alert(4555149)</script>`
2. Confirm the server responds with HTTP 200 but the served `index.html` does **not** contain `<script>alert(4555149)</script>` — it should contain a valid base64 CSRF token instead
3. Confirm normal login flow still works: a fresh browser session (no `csrftoken` cookie) should receive a generated token and the app should load without errors
4. Confirm the `x-rdp-ct` header on subsequent XHR requests from the client matches the safe token in the response cookie
