The formula Five signals. One score.

IDS is computed in computeIDS() at frontend/src/components/chat/IntelligenceDashboard.tsx:15. Each signal is capped at 1.0 before weighting. The weights sum to exactly 1.0.

×0.30
Answer Quality
overallSuccessRate × 0.30
Fraction of queries answered (not blocked) over the current window. The single highest-weight signal — a system that can't answer questions provides no value.
↑ Add documentation for top blocked topics from npm run eval -- --blocked
×0.20
Memory Breadth
min(clusters / 8, 1) × 0.20
Number of recurring question clusters in /api/memory, capped at 8. Each cluster is a topic this org revisits repeatedly — evidence that the knowledge is being used, not just indexed.
↑ Grows naturally as teams ask questions over weeks — cannot be gamed by bulk indexing
×0.15
Query Volume
min(totalQueries / 50, 1) × 0.15
Raw usage signal, normalized against a threshold of 50 queries. Proves the hub is in daily workflow, not just installed. Caps at 1.0 so volume alone cannot inflate IDS.
↑ Onboard additional team members; add the VS Code extension to surface the hub in context
×0.15
Gap Pressure
(1 − gapRatio) × 0.15
Inverse of the blocked-query ratio. An org with no blocked questions scores full marks here. High gap pressure (gapRatio > 0.4) strongly depresses IDS and surfaces documentation debt.
↑ Use /api/gaps/outline to generate docs for the top blocked topics
+0.10
Risk Baseline & Section Health
riskData ? +0.10 : 0   +   (avgHealth / 100) × 0.10
Two smaller signals: a flat +0.10 bonus for having risk data at all (proving the knowledge map has been analyzed), plus 10% weighted by average section health score. Together these reward organizational maintenance discipline, not just usage volume.
The risk baseline is a step function — it adds 0.10 the moment /api/knowledge/risk has been run, regardless of the results. Run it once before any customer review.
The threshold What 0.70 looks like in practice

Crossing 0.70 requires a specific combination of signals — it cannot be gamed by inflating one number. The math below shows the minimum realistic profile needed.

A representative 0.72 IDS profile

Answer quality: 90% success rate  (0.90 × 0.30) 0.27
Memory breadth: 6 clusters  (6/8 × 0.20) 0.15
Query volume: 50+ queries  (1.0 × 0.15) 0.15
Gap pressure: 5% blocked rate  (0.95 × 0.15) 0.14
Risk baseline: established  (+0.10) 0.10
Section health: 75% average  (0.75 × 0.10) 0.075
Total IDS 0.715

To reach 0.715, this org needed at least 50 queries, 6 distinct recurring topics, 90%+ answer success, and active maintenance (risk baseline + section health). These are signals of an org that has been running the hub in real workflows for 30–60 days — not a new install.

The window Why 90 days matters

The 90-day accumulation window

A competitor could copy every feature in the product in 90 days. They cannot copy 90 days of an organization's actual query history, gap patterns, memory clusters, and retrieval decisions. Those signals are derived from real work — they require time and real usage to form.

The moat is not the software. The moat is the intelligence layer that grows from using it. At IDS ≥ 0.70, leaving would mean starting that accumulation over from zero — and losing 90 days of organizational memory that is not stored anywhere else.

The /api/intelligence/history endpoint tracks IDS week-over-week. The delta between snapshots shows whether the moat is strengthening, stable, or eroding. Any downward trend before 0.70 is a churn signal worth acting on within the same week.

What drags IDS down The three IDS killers
🚫
High blocked rate
A blocked rate above 40% means the answer quality signal (×0.30) and gap pressure signal (×0.15) are both depressed simultaneously. IDS is structurally capped well below 0.70.
Fix: identify the top 5 blocked topics from eval.jsonl and create documentation for each before the next review cycle.
💀
Dead sections
Sections with no answered queries in 30+ days are flagged as dead by /api/knowledge/risk. They reduce average section health, eroding the health signal. They also pull down answer rate if queries are directed at them.
Fix: PATCH /api/health/section/:name with "priority": "ignore" to exclude dead sections from retrieval while rebuilding their docs.
👤
Single-user pattern
If only one person is asking questions, the query volume signal hits its ceiling but the memory clusters never diversify. IDS is bounded because the system only knows one person's knowledge gaps — not the organization's.
Fix: onboard a second team member in the first two weeks. Even 5 queries from a different perspective creates new memory clusters.
