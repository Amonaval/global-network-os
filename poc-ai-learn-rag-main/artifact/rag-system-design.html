How a question travels through the RAG engine

A stage-by-stage map of the retrieval pipeline as it is actually built — a hand-rolled hybrid RAG in plain Node.js, no LangChain or LlamaIndex. Follow the two paths: documents flowing in, a question flowing out as a cited answer.

Type: Hybrid Retrieval RAG Retrieval: BM25 + Cosine → RRF Store: sharded JSON LLM: Ollama · Claude · vLLM Embed: Nomic · TF-IDF · OpenAI

01 The write path — ingestion

Runs once per crawl or upload (npm run ingest). Raw sources become clean, self-locating, embedded chunks sitting in the vector store, partitioned by section.

1

Source fetch

Three source types selected at setup: a crawled web portal (Playwright), Confluence (API token or OAuth), or a list of URLs. Uploaded files (PDF/DOCX/TXT/MD/HTML/ZIP) enter the same pipeline via /api/docs/upload.

2

Clean & extract

extractText() in cleaner.js strips nav/footer/TOC noise with cheerio and converts <table> to markdown via tableToMarkdown(). File-type extractors live in src/ingestion/extractors/.

3

Chunk

chunkText() estimates tokens (chars ÷ 4), splits on blank lines, merges table blocks so they never break, then greedily fills to chunkSize with chunkOverlap. Each chunk gets a breadcrumb prefix and nearHeading metadata.

4

Embed

getEmbedder() factory: Nomic (nomic-embed-text, 768-dim, batches of 32) by default, TF-IDF (2048-dim hashed, pure-JS fallback), or OpenAI (text-embedding-3-small, 1536-dim).

5

Vector store upsert

getVectorStore() writes records { id, text, meta, embedding } into vectors_<section>.json. The id is a sanitized section__title__chunkIndex — used for dedup on re-ingest and for chunk pinning. A dimension mismatch (768/1536/2048) forces a full re-index.

02 The read path — query

Runs on every chat message (query() / queryStream() in src/rag/query.js). A question is embedded, matched two ways, gated for confidence, compressed to a token budget, then answered with inline [n] citations that map 1:1 to the returned sources.

retrieval & generation confidence gate (blocks out-of-scope)
1

Embed & retrieve

The question is embedded once, then store.search() scores every candidate by cosine similarity and by BM25 (the raw question text is passed via setQuery()). An optional sections[] filter scopes retrieval to chosen partitions.

2

RRF fusion + priority

rrf() (k=60) fuses the two ranked lists; HYBRID_WEIGHT selects pure-semantic (0), pure-BM25 (1), or RRF (between). applyPriorityMultipliers() then boosts (×1.3) or de-prioritizes (×0.4) sections per data/section_config.json.

3

Confidence gate

Blocks out-of-scope questions before spending an LLM call: passes if topSemScore ≥ CONFIDENCE_GATE or (topRrfScore ≥ 0.014 and topSemScore ≥ 0.05). On block, it returns near-miss section suggestions. Pinned chunks skip this step.

4

Context compression

compressContext(): drop chunks below MIN_SCORE, dedup pairs sharing >60% of trigrams (Jaccard), greedily fill a ~1800-token budget, and tag each kept chunk [1]…[n] — the same numbers the model is told to cite.

5

Generate & stream

Provider fan-out (Ollama / Claude / vLLM), temperature 0.15, streamed token-by-token over SSE. A DEFLECTION_PATTERNS check flags "soft-blocked" answers post-hoc. Returned sources[] line up 1:1 with the [n] citations, and every query appends a row to data/eval.jsonl.

04 The data that moves

Three shapes carry the whole system. The section field is the primary partition key — it is the JSON shard filename, the retrieval filter, and the citation grouping all at once.

// chunk record — in the store

// id = section__title__chunkIndex (sanitized)
{
  id: "api__auth__3",
  text: "**Space:** API › **Page:** Auth\n...",
  meta: {
    title, url, section, breadcrumb,
    spaceKey, pageId, chunkIndex, nearHeading
  },
  embedding: [0.021, -0.118, …] // 768
}

// source — returned to the UI

// sources[n-1] ⟷ inline citation [n]
{ section, title, url, score }

// eval.jsonl — one row per query
{
  ts, question, topSemScore, latencyMs,
  blocked, softBlocked, sectionsUsed,
  usedChunks, budgetUsed, userId
}

One divergence worth reconciling

The confidence-gate default differs by source: config.js ships 0.22 (and configToEnv() projects it to the CONFIDENCE_GATE env var), while query.js's in-code fallback is 0.15. In practice the configured 0.22 wins because the env var is always set — but the two literals should be aligned to a single source of truth to avoid confusion during tuning.
