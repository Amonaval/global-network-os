Part 1
The Data Contract
Every field written to eval.jsonl by query.js, and which endpoints consume each field.

Every query — answered or blocked — appends one JSON line to data/eval.jsonl. The /api/analytics and /api/gaps endpoints aggregate this file on request. The CLI reads it directly. The schema below is the complete authoritative contract.

True when the confidence gate fired (hard block) or when the answer was a deflection (soft block). Hard block: topSemScore < 0.15 AND topRrfScore < 0.014. Soft block: LLM answer matched deflection phrases. The primary signal for answer rate and gap detection.

boolean
True when the LLM generated an answer but it was detected as a deflection ("I don't have information about…"). Subset of blocked. Useful for distinguishing retrieval failures from LLM failures.

Cosine similarity between the query embedding and the top-ranked chunk. Range: 0–1. Confidence gate baseline: 0.15 (env: CONFIDENCE_GATE). Core retrieval quality signal; used in the IDS answer quality component.

integer
End-to-end query latency in milliseconds, from embed start to logEval() call. Includes retrieval, context compression, and LLM generation. P95 latency is the operational SLA target.

string[]
Distinct section names from chunks that passed context compression and were sent to the LLM. Empty array when blocked before reaching the LLM. Drives the "most-used sections" bar chart in the eval CLI summary.

string[]
When a hard block fires, the top 4 sections with closest partial matches. Used to suggest where documentation might exist but is insufficient. Written only on hard blocks; absent on answered queries.

Number of chunks included in the LLM context after compression. Range: 1 to TOP_K (default 6). Written only on answered queries.
debug

integer
Estimated token count of the context string sent to the LLM. Budget cap: 1800 tokens (env: CTX_TOKEN_BUDGET). Computed as chars / 4. Written only on answered queries.
debug

string
Identifier for the user or session that initiated the query. Used for per-user IDS breakdowns in /api/team/ids. May be undefined in CLI or anonymous contexts.

Note on missing fields: There is no answer, sources, or rrfScore field in the logged record. The answer text is not persisted (privacy), sources are reconstructable from sectionsUsed, and rrfScore is not captured at log time. Adding topRrfScore to the log entry would enable richer retrieval analysis without storing PII.

Part 3
The Path Forward
What RAGAS measures, what we have today, and the prioritised steps to close the gap before the first paying customer.

RAGAS defines four evaluation dimensions that distinguish a credible retrieval system from one that merely returns text. The table below shows exactly where Knowledge Hub's current eval loop stands against each dimension.

RAGAS Dimension What it measures KH today Gap
Context Precision Are the retrieved chunks actually relevant to the question? Fraction of retrieved context that matters. Partial
topSemScore is a proxy — it measures similarity of the top chunk, not precision across all retrieved chunks.		 Need per-chunk relevance scoring, not just top-1
Context Recall Did we retrieve all the chunks needed to answer the question correctly? Not measured
No ground-truth answer set exists to verify recall.		 Requires synthetic Q&A dataset generated from indexed docs
Faithfulness Is every claim in the answer grounded in the retrieved context? Partial
Deflection detection (isDeflection()) catches obvious hallucinations but doesn't verify factual grounding.		 Need an LLM-as-judge step that cross-checks each answer sentence against sources
Answer Relevancy Does the answer directly address what was asked? Not measured
No automated scoring of answer-to-question alignment exists.		 Can be approximated by embedding the answer and measuring similarity back to the question
Prioritised implementation steps
1
Add topRrfScore to eval.jsonl
One-line change in logEval() calls in query.js — log the topRrfScore alongside topSemScore. Unlocks hybrid retrieval quality analysis without any architectural change.
1 hour Write path only — no UI change
2
Generate synthetic test dataset from indexed docs
Use Claude Haiku to generate 50–100 (question, ground_truth_answer, source_chunks) triples from indexed content. Store in data/eval_testset.jsonl. This is the prerequisite for Context Recall and Answer Relevancy scoring.
Half day One-time setup, re-run after major ingestion changes
3
Implement Context Precision scoring
After retrieval, embed each retrieved chunk and score its similarity to the query. Log chunkScores[] in eval.jsonl. Mean of non-zero scores = Context Precision proxy. No ground-truth required.
Half day Extends query.js and logEval schema
4
Add answer-relevancy self-score
Embed the LLM answer and score its cosine similarity back to the query embedding (already computed). Log as answerRelevancy. Quick win — uses embeddings already in memory at query time.
2 hours Add one embed call at answer time
5
Wire RAGAS scores into /api/analytics
Once steps 2–4 are complete, add the four RAGAS KPIs to the analytics endpoint response. Expose them in IntelligenceDashboard as a "Retrieval Quality" sub-panel. This is the state needed before any paying customer onboards.
1 day Backend + frontend — feed into IDS formula for stronger signal
