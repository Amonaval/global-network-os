Foundation
Hybrid BM25 + Dense + RRF with Confidence Gate
✓ Implemented

The retrieval foundation combines BM25 keyword matching with dense vector similarity, fused via Reciprocal Rank Fusion (RRF). A dual confidence gate blocks queries with topSemScore < 0.15 AND topRrfScore < 0.014 — preventing hallucinated answers on out-of-scope questions. Context is compressed to 1800 tokens via trigram-based deduplication before reaching the LLM.

◦BM25 catches exact terminology and filename queries that pure vector search misses — critical for Aarav querying a specific integration spec by name
◦Dense embeddings (nomic-embed-text, 768d) handle semantic paraphrase — Anjali asking about "switching treatment protocols" finds chunks about "changing medication plans"
◦The dual confidence gate is the professional liability safeguard — never answer confidently when both signals are weak
◦Priority multipliers in applyPriorityMultipliers() let sections be boosted or muted without re-ingestion

Contextual Chunk Enrichment
→ Next high-value improvement

Before embedding, each chunk is prepended with an LLM-generated sentence describing where it sits within the full document — the project, the client, the decision context. This single change is the most impactful retrieval improvement available without architectural change.

◦Fixes the most common KH failure: fragments like "it reduced latency by 40%" are meaningless without knowing which client engagement and which architecture choice
◦Implementation: one fast LLM call per chunk at ingest time (Claude Haiku or Ollama local model) — zero change to query path
◦Cost: ~0.5–2ms per chunk at ingest, zero latency at query time
◦Decision D.12 in .claude/.engineering/DECISIONS.md

Cross-Encoder Reranking
→ After contextual enrichment

After hybrid retrieval returns 20–50 candidates, a cross-encoder re-scores each chunk jointly with the query, selecting only the top 5–10 for the LLM. Unlike embedding similarity (which scores each chunk independently), a cross-encoder reads the query and the chunk together — catching relevance relationships that independent encoders miss.

◦Model: cross-encoder/ms-marco-MiniLM-L-6-v2 — self-hosted, free, ~80MB, ~5ms inference
◦Directly strengthens the KH precision-over-recall mandate (D.4) — professional liability risk decreases when the top-5 context is tighter
◦10–25% additional precision gain on top of the hybrid + contextual enrichment stack
◦Decision D.13 in .claude/.engineering/DECISIONS.md

RAGAS Evaluation Pipeline
→ Required before customer onboarding

RAGAS measures what the current eval loop cannot: whether retrieved chunks were actually relevant (Context Precision), whether we retrieved everything needed (Context Recall), whether every claim in the answer is grounded in context (Faithfulness), and whether the answer directly addressed the question (Answer Relevancy). These four dimensions are the difference between "it seems to work" and "we can prove it works."

◦Context Precision — fraction of retrieved context that was actually used in the answer
◦Context Recall — did we retrieve all the evidence needed? Requires a synthetic test set from indexed docs
◦Faithfulness — is every claim in the answer grounded in the retrieved context, not in LLM world knowledge?
◦Answer Relevancy — does the answer address the question, not a tangentially related topic?
◦These scores feed directly into the IDS formula — a stronger observability layer means a more credible IDS number for customer conversations

Document-Type Chunking & Multimodal RAG
◌ Future — after Stage 1 validation

Different document types have fundamentally different semantic structures. Legal contracts have hierarchical clause trees. Medical records have structured note formats. Financial filings have table-heavy layouts. Stage 2 introduces chunkers that respect these structures, plus multimodal embeddings that can handle charts, tables, and scanned figures.

◦Document-type chunking: hierarchical parent-child chunking for contracts (retrieve the clause, return the section); semantic paragraph boundaries for medical notes
◦Multimodal: Cohere embed-v4 or Voyage-multimodal-3.5 for PDF charts and scanned figures — Dr. Priya's experiment logs contain graphs that pure text chunking completely ignores
◦Prerequisite: RAGAS evaluation from Stage 1C must be in place so we can measure the delta from these changes

GraphRAG (Legal & Medical) + Agentic Multi-Hop
◌ Stage 3+ — enterprise vertical expansion

GraphRAG represents a structural shift: relationships between entities (parties in a case, drugs in a protocol, precedents cited) are stored as a knowledge graph, enabling queries that traverse entity relationships across documents. Agentic multi-hop adds iterative retrieval loops — the system decomposes complex queries, retrieves and grades intermediate results, and re-queries if evidence is insufficient.

◦GraphRAG: Microsoft's pattern (Neo4j + Qdrant) maps entity relationships — Marcus can ask "which cases cite the same precedent as Smith v. Jones" and get a graph traversal, not just a keyword match
◦LightRAG as a cost-efficient alternative — reported 10x lower cost than Microsoft's implementation with comparable quality for smaller knowledge graphs
◦Agentic multi-hop: Dr. Priya can ask "do any of my experiments conflict with the 2023 Chen paper I indexed?" — triggers multi-hop retrieval across experiment logs and paper excerpts
◦LangGraph orchestration considered only here — the complexity is justified at this stage; it is explicitly out of scope for Stages 0–2

What we deliberately do not build

Every item below is a valid technology. None of them serve a named persona in Knowledge Hub's customer set. Pursuing them would dilute the vertical depth that is our only defensible moat.

✗AST-based code chunking — no customer queries a codebase as a structural graph
✗Function call graph traversal and class inheritance indexing — code architecture navigation
✗Code generation quality improvements — we are not competing with GitHub Copilot
✗LangGraph agent orchestration at Stage 1 or 2 — complexity without validated need
✗"Engineering Intelligence Platform" positioning — Forrester category conflict, misaligns with regulated professional focus
✗General-purpose web search RAG — private organizational memory only
