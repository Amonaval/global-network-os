01 · Prerequisites

Before You Start

Three things must be running before the platform will work. Node.js handles the server and build tools; Ollama provides the local LLM and embedding models; everything else is installed by npm.

1
Node.js 18 or later
Check with node -v. Install from nodejs.org if needed — LTS version preferred. npm comes bundled.
2
Ollama with required models
Install from ollama.com and pull the two models the app uses by default: 
ollama pull qwen2.5:3b     # LLM for chat + codegen
ollama pull nomic-embed-text       # Embedding model (768d vectors)
Verify Ollama is running at http://localhost:11434 — the app health check calls GET /api/app/status which pings Ollama on startup.
3
Optional: Claude API key (for cloud LLM)
Set CLAUDE_API_KEY in your .env file. Without it, the app falls back to Ollama for all LLM calls. This is fine for development — Ollama is the default provider.

02 · Quick Start

Running Locally

The development stack is two processes: the Express server (port 3000) and the Vite dev server (port 5173). Run them together with a single command.

# 1. Install dependencies
npm install

# 2. Set up environment
cp .env.example .env
# Open .env and fill in CLAUDE_API_KEY if using cloud LLM (optional)

# 3. Start both server + Vite concurrently
npm run dev:all
# Express: http://localhost:3000
# React:   http://localhost:5173
First run? Navigate to http://localhost:5173 and the app will prompt you to run the setup wizard. The wizard configures your LLM provider, crawl URL, and creates the data/ directory with initial content.

To run just the server (no frontend dev server), use npm run server. To run the built production frontend, run npm run build:ui first — the Express server will serve dist/ as static files. For the Electron desktop app, use npm run electron (server must already be running).

05 · Frontend Architecture

React, State & Data Fetching

The frontend is React 19 + TypeScript + Vite. All API calls go through typed React Query hooks in useApi.ts. Application state lives in Zustand stores. There are no Redux patterns here.

React Query — the data layer

Every server resource is a typed hook in frontend/src/hooks/useApi.ts. The pattern is consistent:

Hook pattern (read query)

export function useGaps() {
  return useQuery({
    queryKey: ['gaps'],
    queryFn:  () => apiFetch<GapsResponse>('/api/gaps'),
    staleTime: 60_000,            // ms before refetch on re-focus
  })
}

// In a component:
const { data, isLoading, error } = useGaps()
if (isLoading) return <Spinner />
if (error)     return <ErrorBanner error={error} />

Hook pattern (mutation)

export function usePatchHealthSection() {
  const qc = useQueryClient()
  return useMutation({
    mutationFn: ({ name, priority }: PatchHealthArgs) =>
      apiFetch(`/api/health/section/${name}`, {
        method: 'PATCH',
        body: JSON.stringify({ priority }),
      }),
    onSuccess: () => qc.invalidateQueries({ queryKey: ['health'] }),
  })
}

Zustand stores

Two stores. Use the appropriate one — don't store server data in Zustand (that's React Query's job).

appStore.ts
Active section, sidebar state, theme toggle, chat session ID, filter bar selections (time window, section, user, status). Everything that affects which data the UI shows.
wizardStore.ts
Setup wizard step (1–5), form values for each step (provider, URL, credentials), build progress state. Cleared when the wizard completes.

06 · Adding an Endpoint

How to Add a Server Route

All routes are registered in src/api/server.js. Each route reads from a data source (eval.jsonl, a JSON file, the vector store) and returns JSON. The pattern is consistent across all 40+ existing routes.

1. Register the route in server.js
app.get('/api/my-feature', async (req, res) => {
  try {
    const result = await computeMyFeature(req.query)
    res.json({ data: result, ok: true })
  } catch (err) {
    console.error('[my-feature]', err)
    res.status(500).json({ error: err.message })
  }
})
2. Add a typed hook in useApi.ts
// Define the response type
interface MyFeatureResponse {
  data: { field: string }[]
  ok: boolean
}

// Export the hook
export function useMyFeature() {
  return useQuery({
    queryKey: ['my-feature'],
    queryFn:  () => apiFetch<MyFeatureResponse>(
      '/api/my-feature'
    ),
    staleTime: 60_000,
  })
}
Convention: Log all errors with a module prefix in brackets — [my-feature] — so grep in server logs finds them immediately. Return { error: err.message } with a 4xx/5xx status, never an empty 200.

07 · Adding an Intelligence Panel

How to Add a New Intelligence Panel

Each intelligence panel is a React component in frontend/src/components/chat/ that uses one or more hooks from useApi.ts. The sidebar navigation registers panels in appStore.ts.

1
Add the API endpoint (see §06)
Build and test GET /api/my-panel and add the typed hook useMyPanel() in useApi.ts.
2
Create the panel component
Create frontend/src/components/chat/MyPanel.tsx. Follow the existing panel structure: 
export function MyPanel() {
  const { data, isLoading, error } = useMyPanel()

  if (isLoading) return <PanelSkeleton />
  if (error)     return <PanelError error={error} />
  if (!data)     return null

  return (
    <div className="panel">
      <h2>My Panel</h2>
      // Your panel content here
    </div>
  )
}
3
Register in the navigation
Add an entry to the panels array in appStore.ts (or wherever the sidebar nav items are defined — check how GapsPanel, MemoryPanel etc. are registered). The entry needs an id, label, icon, and the component reference.
4
Wire the panel into the router / switch
In ChatLayout.tsx (or the equivalent panel switcher), add a case for the new panel id that renders <MyPanel />.

08 · Data Files Reference

What Lives in data/

The data/ directory is git-ignored and created by the app at runtime. It holds all runtime state. Here is every file, its format, and which part of the system writes and reads it.

FileFormatWritten byRead byRole
eval.jsonl Append-only JSONL query.js (logEval) eval.js, all intelligence endpoints runtime The source of all intelligence. One line per query: ts, question, blocked, softBlocked, topSemScore, latencyMs, sectionsUsed, nearMissSections, usedChunks, budgetUsed, userId
vectors_*.json JSON array ingest pipeline query.js (retrieval) generated One file per knowledge section. Contains chunk text, embedding vectors, metadata (source URL, file path, title, position). Do not edit manually — re-ingest if you change them.
decisions.json JSON array POST /api/decisions/extract GET /api/decisions generated LLM-extracted architectural decisions. Each record: id, title, context, decision, alternatives, consequences, section, extractedAt.
sessions.json JSON object POST /api/chat POST /api/chat (history) runtime Keyed by sessionId. Each session stores up to 8 prior turns for context window injection.
intelligence_history.json JSON array POST /api/intelligence/snapshot GET /api/intelligence/history runtime Weekly IDS snapshots for the sparkline trend chart. Each entry: ts, ids, totalQueries, answerRate, clusterCount, gapRatio.
crawl_hashes.json JSON object crawl pipeline Maintenance panel cache URL → MD5 hash map. Used by incremental crawl to skip unchanged pages and by the Maintenance panel to detect staleness.
app_config.json JSON object POST /api/app/config, setup wizard config.js (startup) config User-chosen settings: LLM provider, model, Ollama URL, embedding model, portal URL, section list, boost/ignore priorities.
users.json JSON array POST /api/users Team IDS endpoint, Analytics config Registered users for multi-user / team mode. Each entry: id, name, email, role, createdAt.
Never commit data/ — it contains real query logs and potentially sensitive document vectors. The .gitignore excludes the entire directory. If you accidentally stage a file from data/, run git rm --cached data/<file> before committing.

09 · Architectural Decisions

What Is Already Decided

These decisions are locked. Understanding the why behind each one prevents accidentally reversing them. For the full decision records with context and alternatives, read .claude/.engineering/DECISIONS.md.

D.01Local-first, single-user by default
All data lives in data/ on the user's machine. No cloud sync, no SaaS backend. This is the core privacy guarantee and the primary differentiator vs. every hosted RAG platform.
Locked — reverting this means becoming AnythingLLM, which already exists and is free.
D.02Hybrid BM25 + Dense + RRF retrieval
BM25 handles keyword precision; dense vectors handle semantic similarity; RRF fuses them at weight 0.5/0.5. Both retrieval paths run in parallel and are fused before the confidence gate. Do not replace with pure BM25 or pure vector search.
Locked — the hybrid system provides ~20% better coverage than either alone at our corpus sizes.
D.03Confidence gate before LLM — dual condition
The gate: topSemScore >= 0.15 OR (topRrfScore >= 0.014 AND topSemScore >= 0.05). Do not make the gate a simple threshold — the dual condition exists to catch queries where BM25 is confident but dense similarity is moderate (technical queries with exact keyword matches).
Locked — gating is what makes blocked queries into documentation gap signals, which drives the Gaps panel.
D.04eval.jsonl is append-only
logEval() only appends. Intelligence panels always read the full log and aggregate in memory. This means the log grows unboundedly — the trade-off for never losing historical data.
Locked — compaction or truncation would destroy historical intelligence and break the IDS trend sparkline.
D.05No AST or code graph traversal in RAG
Knowledge Hub does not index code semantically at the AST level, does not traverse import graphs, and does not chunk by function boundaries. Code is treated as text. Engineering documents (READMEs, DECISIONS.md, architecture docs) are the unit of knowledge, not code files.
Locked per RAG_STRATEGY.md — this is a deliberate scope boundary, not a gap. The roadmap has code intelligence as a separate capability (Stage 3+).
D.06React Query is the data layer — Zustand is UI state only
Server-sourced data (sections, health scores, gaps, IDS) lives in React Query caches. Zustand holds only local UI state (selected section, sidebar open/closed, filter bar values, wizard step). Never store server responses in Zustand stores.
Locked — mixing the two causes cache invalidation bugs and double-fetching.

10 · Eval & Debugging

Diagnosing Problems

Two CLI tools help you understand what the pipeline is doing without opening the UI.

npm run eval — analyze the query log

npm run eval -- --summary                    # Total queries, answer rate, latency p50/p95
npm run eval -- --blocked                    # Show blocked queries and their topSemScore
npm run eval -- --tail 50                    # Last 50 entries from eval.jsonl
npm run eval -- --section "Engineering Docs" # Queries that hit this section only

npm run diagnose — check system health

npm run diagnose
# Checks:
#  - Ollama reachable at configured URL
#  - Embedding model (nomic-embed-text) loaded and returning correct vector dimensions
#  - Vector files exist for all configured sections
#  - Dimension mismatch between stored vectors and current embedding model
#  - data/ directory present and writable
#  - eval.jsonl accessible (for intelligence panels)

Common issues

Everything returns blocked (empty gaps panel shows many blocks)
Ollama is running but the embedding model isn't loaded. Run ollama pull nomic-embed-text. Also check that OLLAMA_BASE_URL in .env matches the Ollama port.
Intelligence panels show "no data" after ingestion
The panels read eval.jsonl, not the vectors. You must ask at least a few questions through the chat interface to populate the log. The vector store is built correctly when ingestion succeeds.
Vector dimension mismatch error
You changed the embedding model in config but still have old data/vectors_*.json files. Delete them and re-ingest. The diagnose tool will confirm the mismatch and tell you which section is affected.
Frontend not connecting to server (CORS or 502)
In development, the Vite dev server at :5173 proxies API calls to :3000. If the server isn't running, you'll get a 502. Always start both with npm run dev:all, not npm run dev alone.

11 · Before Shipping

The Completion Questions

Ask these four questions at the end of every meaningful engineering session. They are not checkboxes — answer each one honestly before closing the work.

1
Did we solve the right problem? Could the user's real need have been addressed at a higher level — product, architecture, or process — without this code?
2
Is there a more transformative opportunity here? Does what we just built reveal a larger capability that would be more valuable to build next?
3
Should the roadmap change? Does this session's work shift the prioritization of anything in .product/05_WORK_QUEUE.md or .product/07_FEATURE_BACKLOG.md?
4
What knowledge should be preserved? Update .product/06_PROGRESS.md, .product/04_NEXT_MISSION.md, and .product/01_CEO_DASHBOARD.md. Only update if there is genuinely new knowledge — never update for the sake of updating.
